spring boot restful crud using "ApplicationContextInitializer" example

ApplicationContextInitializer is typically used in integration tests to provide a dynamic and consistent testing environment (e.g., configuring a test database using Testcontainers) rather than for building the main production CRUD application logic itself. The core logic of a Spring Boot RESTful CRUD service uses standard Spring annotations like @RestController, @Autowired, @Service, and @Repository. 

Below is a combined example demonstrating a standard Spring Boot CRUD API, along with a testing example using an ApplicationContextInitializer.

1. The Standard Spring Boot RESTful CRUD Application
This is the main application code for a simple "Product" CRUD API.

Product.java (Entity)
java
package com.example.crud.model;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    private double price;

    // Standard getters, setters, constructors
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public double getPrice() { return price; }
    public void setPrice(double price) { this.price = price; }

package com.example.crud.controller;

2. Using ApplicationContextInitializer in Integration Tests

This is where ApplicationContextInitializer is typically used. It can dynamically configure environment properties for tests, such as redirecting the application's database connection to a temporary container managed by Testcontainers. 

ProductControllerIT.java (Integration Test)

This example requires the testcontainers dependency.
java
package com.example.crud;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.test.context.ContextConfiguration;
import org.springframework.test.context.support.TestPropertyValues;
import org.springframework.test.web.reactive.server.WebTestClient;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@Testcontainers
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ContextConfiguration(initializers = ProductControllerIT.Initializer.class) // Link the initializer

public class ProductControllerIT {

    @Autowired
    private WebTestClient webTestClient; // Used for calling REST endpoints

    @Container // Manages the lifecycle of the Docker container
    public static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:13")
            .withDatabaseName("testdb")
            .withUsername("testuser")
            .withPassword("testpass");

    // The ApplicationContextInitializer implementation
    static class Initializer implements ApplicationContextInitializer<ConfigurableApplicationContext> {
        @Override
        public void initialize(ConfigurableApplicationContext configurableApplicationContext) {
            // Dynamically set Spring properties to use the Testcontainers instance
            TestPropertyValues.of(
                    "spring.datasource.url=" + postgres.getJdbcUrl(),
                    "spring.datasource.username=" + postgres.getUsername(),
                    "spring.datasource.password=" + postgres.getPassword()
            ).applyTo(configurableApplicationContext.getEnvironment());
        }
    }
    
    // An example test case
    @Test
    void whenGetAllProducts_thenStatusIsOk() {
        webTestClient.get().uri("/api/products")
                .exchange()
                .expectStatus().isOk();
                // Add further assertions here
    }
}

=========================================
The @Container annotation is not a standard Spring Boot annotation. It is most commonly associated with Testcontainers, a Java library that provides lightweight, throwaway instances of databases, message brokers, web browsers, or anything else that can run in a Docker container.
Here is an example of how @Container is used with Testcontainers in a Spring Boot application for integration testing:
1. Add Testcontainers Dependency:
Include the necessary Testcontainers dependency in your pom.xml (for Maven) or build.gradle (for Gradle). For example, for a PostgreSQL database:
Code

<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <version>1.19.3</version> <!-- Use the latest version -->
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>1.19.3</version> <!-- Use the latest version -->
    <scope>test</scope>
</dependency>
2. Create a Test Class with @Container:
Java

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@SpringBootTest
@Testcontainers // Enables Testcontainers for the test class
class MyServiceIntegrationTest {

    @Container // Marks this field as a Testcontainers container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine")
            .withDatabaseName("testdb")
            .withUsername("testuser")
            .withPassword("testpass");

    @DynamicPropertySource // Configures Spring properties dynamically
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private MyService myService; // Your Spring Boot service to be tested

    @Test
    void testMyServiceMethod() {
        // Perform actions and assertions using myService, which will now
        // interact with the Testcontainers-managed PostgreSQL instance.
        // For example:
        // myService.saveData("some data");
        // List<String> data = myService.getAllData();
        // assertThat(data).contains("some data");
    }
}
Explanation:

@Testcontainers: This annotation on the test class enables Testcontainers support.

@Container static PostgreSQLContainer<?> postgres: This declares a static field of type 
PostgreSQLContainer and annotates it with @Container. Testcontainers will automatically start and stop this container before and after the test class executes.

postgres:15-alpine: Specifies the Docker image to use for the PostgreSQL container.
withDatabaseName, withUsername, withPassword: Configures the database details within the container.

@DynamicPropertySource: This method is used to dynamically configure Spring Boot properties at runtime. It's crucial for making your Spring Boot application connect to the Testcontainers-managed database.

registry.add(...): Adds properties like the JDBC URL, username, and password, retrieving them directly from the running postgres container.

WebTestClient

WebTestClient is a non-blocking, reactive client for testing web servers in Spring applications, particularly useful for Spring Boot applications. It leverages the reactive WebClient internally to perform requests and offers a fluent API for verifying responses. 
Key Features and Usage in Spring Boot:
Integration with Spring Boot Testing: When using @SpringBootTest with Spring WebFlux on the classpath, Spring Boot automatically configures a WebTestClient instance that targets the locally running Spring Boot application.
Testing against MockMvc: Since Spring Boot 2.4 (Spring Framework 5.3), WebTestClient can also be used to test against a MockMvc environment, allowing for reuse of request specifications between integration tests and controller-level tests.
Fluent API for Assertions: WebTestClient provides a fluent API for setting up requests and verifying responses, making tests concise and readable.
Reactive Nature: Designed for testing reactive web applications built with Spring WebFlux, it handles asynchronous operations and streaming responses effectively.
Binding to ApplicationContext: When testing, WebTestClient can be bound to the ApplicationContext of the application under test, allowing it to interact with the application's components during the test execution.
Example Usage:
Java

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.reactive.AutoConfigureWebTestClient;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.MediaType;
import org.springframework.test.web.reactive.server.WebTestClient;

@SpringBootTest
@AutoConfigureWebTestClient // Autoconfigures WebTestClient for @SpringBootTest
public class MyControllerIntegrationTest {

    @Autowired
    private WebTestClient webTestClient;

    @Test
    void testGetEndpoint() {
        webTestClient.get().uri("/api/myresource")
            .accept(MediaType.APPLICATION_JSON)
            .exchange()
            .expectStatus().isOk()
            .expectHeader().contentType(MediaType.APPLICATION_JSON)
            .expectBodyList(MyResource.class).hasSize(2); // Assuming MyResource is a DTO
    }

    @Test
    void testPostEndpoint() {
        MyResource newResource = new MyResource("test-name"); // Assuming MyResource is a DTO
        webTestClient.post().uri("/api/myresource")
            .contentType(MediaType.APPLICATION_JSON)
            .bodyValue(newResource)
            .exchange()
            .expectStatus().isCreated()
            .expectHeader().location("/api/myresource/some-id"); // Assuming a location header is returned
    }
}

2. The Integration Test with ApplicationContextInitializer
This is where the ApplicationContextInitializer comes into play. It will configure the application context just before the tests run to use the dynamic details of the test database. 
java
package com.example.demo;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.test.context.ContextConfiguration;
import org.springframework.test.context.support.TestPropertyValues;
import org.springframework.test.web.reactive.server.WebTestClient;
import org.junit.jupiter.api.Test;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@Testcontainers
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ContextConfiguration(initializers = ProductControllerIT.Initializer.class)
public class ProductControllerIT {

    // Use a static container so it's shared across all tests in this class
    @Container
    public static PostgreSQLContainer<?> postgreSQLContainer = new PostgreSQLContainer<>("postgres:13.3")
            .withDatabaseName("testdb")
            .withUsername("testuser")
            .withPassword("testpass");

    @Autowired
    private WebTestClient webTestClient;

    /**
     * The ApplicationContextInitializer implementation.
     * It runs before the Spring ApplicationContext is refreshed.
     */
    static class Initializer implements ApplicationContextInitializer<ConfigurableApplicationContext> {
        public void initialize(ConfigurableApplicationContext configurableApplicationContext) {
            TestPropertyValues.of(
                    "spring.datasource.url=" + postgreSQLContainer.getJdbcUrl(),
                    "spring.datasource.username=" + postgreSQLContainer.getUsername(),
                    "spring.datasource.password=" + postgreSQLContainer.getPassword()
            ).applyTo(configurableApplicationContext.getEnvironment());
        }
    }

    @Test
    void canCreateProduct() {
        // Example test using WebTestClient to perform a POST request
        webTestClient.post().uri("/api/products")
                .bodyValue(new Product(null, "Test Product", 19.99))
                .exchange()
                .expectStatus().isOk()
                .expectBody()
                .jsonPath("$.name").isEqualTo("Test Product");
    }
}

In this pattern, the Initializer class is solely responsible for bridging the gap between the dynamically started Testcontainers database and Spring's configuration, allowing the standard CRUD code to run without needing to know about the testing environment specifics. 
===================================================

The code snippet @ContextConfiguration(initializers = ProductControllerIT.Initializer.class) / using @container illustrates a testing pattern in a Spring Boot application using the Testcontainers library to provide external services (like a database or message broker) for integration tests. 
This approach ensures that the external service is available and configured before the Spring application context is fully loaded. 
Key Components
@ContextConfiguration(initializers = ...): This Spring annotation declares the ApplicationContextInitializer classes used to configure the application context for the test. In this pattern, the initializer is responsible for starting a Docker container and registering its dynamic connection properties (e.g., host, port, credentials) into the Spring Environment.
ProductControllerIT.Initializer: This is a static nested class within the ProductControllerIT test class (or a separate class) that implements the ApplicationContextInitializer interface. Its initialize method contains the logic to:
Define and start the Testcontainers container (e.g., a PostgreSQLContainer).
Obtain the dynamically generated connection details from the running container.
Add these details as properties (like spring.datasource.url, spring.datasource.username, etc.) to the Spring application context's Environment.
@Container: This annotation from org.testcontainers.junit.jupiter is used on a field (typically a static field in this pattern) to denote a container managed by the Testcontainers JUnit 5 extension. It handles the container lifecycle (start and stop). When used on a static field, the container starts once before all tests in the class run and stops after all tests are finished.
/ using @container: This appears to be a comment in the user's code, indicating that the @Container annotation is being used in conjunction with the @ContextConfiguration initializer pattern. The two work in concert: @Container manages the container lifecycle, while the Initializer integrates the container's dynamic configuration into Spring's context. 
Modern Alternative: @DynamicPropertySource
A more modern and less verbose approach (introduced in Spring Framework 5.2 and common in newer Spring Boot versions) uses the @DynamicPropertySource annotation alongside @Testcontainers and @Container annotations. This approach reduces boilerplate code by dynamically registering properties via a method. 
java
@SpringBootTest
@Testcontainers // Activates Testcontainers JUnit 5 extension
class ProductControllerIT {

    // Container lifecycle managed by @Testcontainers and @Container
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:latest");

    // Dynamic property registration
    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    // ... test methods
}
This newer method is generally recommended, although the ApplicationContextInitializer pattern is still valid and offers more flexibility in some complex scenarios, such as when containers need to be shared across many test classes via an interface.

spring boot ApplicationContextInitializer example

An ApplicationContextInitializer in Spring Boot is used for programmatic configuration of the ApplicationContext before it is fully refreshed. Common use cases include adding custom property sources, activating specific profiles, or performing other setup logic that must occur early in the application lifecycle. 

1. Implementation
First, create a Java class that implements the ApplicationContextInitializer interface and overrides the initialize method. This example adds a custom property to the application's environment. 
java
package com.example.demo;

import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.core.env.ConfigurableEnvironment;
import org.springframework.core.env.MapPropertySource;

import java.util.Collections;
import java.util.Map;

public class CustomApplicationContextInitializer implements 
        ApplicationContextInitializer<ConfigurableApplicationContext> {

    @Override
    public void initialize(ConfigurableApplicationContext applicationContext) {
        ConfigurableEnvironment environment = applicationContext.getEnvironment();
        Map<String, Object> customProps = Collections.singletonMap("custom.property.value", "hello from initializer");
        
        // Add the custom property source with a specific name
        environment.getPropertySources().addFirst(new MapPropertySource("customSource", customProps));
        
        System.out.println("Custom ApplicationContextInitializer executed: added 'custom.property.value'");
    }
}

Use code with caution.

2. Registration in Spring Boot

You can register the initializer in two primary ways:

A. Programmatically (per application)
Modify your main SpringBootApplication class to add the initializer to the SpringApplication instance before it runs. 
java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication application = new SpringApplication(DemoApplication.class);
        // Register the custom initializer
        application.addInitializers(new CustomApplicationContextInitializer());
        application.run(args);
    }
}

Use code with caution.
Alternatively, you can use the SpringApplicationBuilder for a fluent API approach. 
java
import org.springframework.boot.builder.SpringApplicationBuilder;

// ... inside main method
new SpringApplicationBuilder(DemoApplication.class)
    .initializers(new CustomApplicationContextInitializer())
    .run(args);

Use code with caution.

B. Declaratively (via spring.factories) 

For an initializer that should apply to all applications that use a specific library, register it in a META-INF/spring.factories file within the library's JAR. This file should contain an entry like this: 

properties
org.springframework.context.ApplicationContextInitializer=com.example.demo.CustomApplicationContextInitializer

Use code with caution.

3. Verification
Once registered and the application runs, the initializer will execute before the context is refreshed. You can verify this by checking the console output for the print statement. Any bean in your application can then access the custom property: 
java

    }

Use code with caution.
Running the application will produce output similar to:

...

Spring Boot provides ApplicationContextInitializer classes as a mechanism to programmatically modify the application context before it is refreshed. This allows for custom configurations and setup that need to occur before the bean lifecycle begins.

Key aspects of ApplicationContextInitializer classes:

Interface Implementation: To create a context initializer, a class must implement the org.springframework.context.ApplicationContextInitializer<C extends 
ConfigurableApplicationContext> interface.

initialize Method: The core of the initializer is the initialize method, which takes a 
ConfigurableApplicationContext as an argument. Within this method, you can perform operations like:
Adding or modifying PropertySource objects to customize environment properties.
Registering bean definitions programmatically.

Adding BeanPostProcessor or BeanFactoryPostProcessor instances.

Performing any other setup required before the context is fully initialized and beans are created.

Registration: Spring Boot automatically detects and applies ApplicationContextInitializer instances in several ways:

spring.factories: Listing the fully qualified class name of your initializer in META-INF/spring.factories under the key org.springframework.context.ApplicationContextInitializer.
Programmatically: Adding initializers to the SpringApplication instance before running it:
Java

        SpringApplication app = new SpringApplication(MyApplication.class);
        app.addInitializers(new MyCustomInitializer());
        app.run(args);

Testing: Using the @ContextConfiguration annotation in tests with the initializers attribute to specify initializer classes.

Ordering: If multiple initializers are present, their execution order can be controlled by implementing the org.springframework.core.Ordered interface or by using the @Order annotation.

When to use ApplicationContextInitializer:
When you need to perform actions that modify the ApplicationContext itself before it's fully set up and beans are created.

For externalizing or dynamically configuring parts of your application's setup that cannot be achieved through standard Spring Boot configuration properties or profiles.
In testing scenarios where you need to set up a specific context state for your integration tests.

An ApplicationContextInitializer in Spring Boot provides a way to programmatically initialize the ConfigurableApplicationContext before it is refreshed. This allows for customization of the application context, such as adding custom property sources, activating profiles, or modifying bean definitions, before the application fully starts.
Here is an example demonstrating how to implement and register an ApplicationContextInitializer:
Java

import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.core.env.ConfigurableEnvironment;
import org.springframework.core.env.MapPropertySource;
import java.util.HashMap;
import java.util.Map;

public class CustomApplicationContextInitializer implements ApplicationContextInitializer<ConfigurableApplicationContext> {

    @Override
    public void initialize(ConfigurableApplicationContext applicationContext) {
        // Get the environment to modify it
        ConfigurableEnvironment environment = applicationContext.getEnvironment();

        // Example 1: Add a custom property source
        Map<String, Object> customProperties = new HashMap<>();
        customProperties.put("my.custom.property", "value from initializer");
        environment.getPropertySources().addFirst(new MapPropertySource("myCustomSource", customProperties));

        // Example 2: Activate a profile based on a condition
        String os = System.getProperty("os.name").toLowerCase();
        if (os.contains("windows")) {
            environment.addActiveProfile("windows-profile");
        } else {
            environment.addActiveProfile("non-windows-profile");
        }

        System.out.println("CustomApplicationContextInitializer executed. Added custom property and activated profile(s).");
    }
}
To register this initializer with your Spring Boot application, you can do so in your main application class:
Java

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class MySpringBootApplication {

    public static void main(String[] args) {
        SpringApplication application = new SpringApplication(MySpringBootApplication.class);
        application.addInitializers(new CustomApplicationContextInitializer());
        application.run(args);
    }
}
In this example:
CustomApplicationContextInitializer implements ApplicationContextInitializer<ConfigurableApplicationContext>.

The initialize method is overridden to contain the custom logic.
Inside initialize, a custom property source named "myCustomSource" is added to the environment with a key my.custom.property.

A profile ("windows-profile" or "non-windows-profile") is activated based on the operating system.
In the main method of MySpringBootApplication, an instance of CustomApplicationContextInitializer is added to the SpringApplication before it is run.

This setup ensures that the custom initialization logic within CustomApplicationContextInitializer is executed very early in the Spring Boot application startup process, allowing for foundational modifications to the application context before bean definitions are processed and the context is fully refreshed.

=================================================

ApplicationContextInitializer in Spring Boot is an interface that allows for programmatic customization of the ApplicationContext before it is refreshed. This means you can modify the environment or the context itself before any beans are instantiated or the application fully starts up.

Key aspects of ApplicationContextInitializer:

Early Customization: It provides a hook to perform actions very early in the Spring application lifecycle, even before the ApplicationContext is fully initialized.
Interface Definition: The interface has a single method: initialize(ConfigurableApplicationContext applicationContext).

Use Cases: Common uses include:

Setting active profiles programmatically.

Adding or modifying PropertySource instances to load custom configuration.

Registering custom BeanDefinitionRegistryPostProcessor or BeanFactoryPostProcessor implementations.
Performing environment-specific setup or pre-configuration tasks.

Registration:

Programmatically: By calling springApplication.addInitializers() before running the SpringApplication.

Declaratively (for all applications): By adding the fully qualified class name of your 

ApplicationContextInitializer implementation to META-INF/spring.factories within a JAR file, making it discoverable by Spring Boot.

Ordering: ApplicationContextInitializer implementations can be ordered using Spring's Ordered interface or the @Order annotation, allowing control over the sequence of initialization.
Example of a custom ApplicationContextInitializer:
Java

import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.core.env.ConfigurableEnvironment;
import org.springframework.core.env.MapPropertySource;

import java.util.Collections;

public class MyCustomInitializer implements ApplicationContextInitializer<ConfigurableApplicationContext> {

    @Override
    public void initialize(ConfigurableApplicationContext applicationContext) {
        ConfigurableEnvironment environment = applicationContext.getEnvironment();
        environment.addActiveProfile("custom-profile"); // Set an active profile
        environment.getPropertySources().addFirst(
            new MapPropertySource("myCustomProperties", 
                Collections.singletonMap("my.custom.property", "customValue"))); // Add a custom property
    }
}
