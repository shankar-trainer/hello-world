An ApplicationContextInitializer is a Spring Framework callback interface used to programmatically initialize a ConfigurableApplicationContext before it gets refreshed and before any bean definitions are loaded.

It is typically used for advanced setup tasks like activating specific profiles or injecting dynamic property sources into the environment.Here is a complete, step-by-step example of how to implement and register a custom initializer.

1. Create the Custom InitializerImplement the ApplicationContextInitializer interface.
In this example, we will dynamically set an active environment profile and inject a custom system property.java

package com.example.demo.initializer;

import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.core.env.ConfigurableEnvironment;
import org.springframework.core.env.MapPropertySource;
import java.util.Map;

public class MyCustomContextInitializer implements ApplicationContextInitializer<ConfigurableApplicationContext> {

    @Override
    public void initialize(ConfigurableApplicationContext applicationContext) {
        // 1. Access the environment
        ConfigurableEnvironment environment = applicationContext.getEnvironment();

        // 2. Programmatically set an active profile
        environment.addActiveProfile("performance-mode");

        // 3. Inject a dynamic runtime property
        Map<String, Object> customProperties = Map.of("dynamic.api.timeout", "5000");
        MapPropertySource propertySource = new MapPropertySource("myCustomSource", customProperties);
        environment.getPropertySources().addFirst(propertySource);

        System.out.println(">>> MyCustomContextInitializer: Context initialized successfully!");
    }
}
Use code with caution.
2. Register the InitializerBecause this runs before the application context is fully created, annotating the class with @Component will not work automatically for global startup.

You must register it using one of the three options below:

Option A: Register in main (Recommended for Spring Boot)
Pass the initializer directly to your SpringApplication instance inside your main method.
java
package com.example.demo;

import com.example.demo.initializer.MyCustomContextInitializer;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(DemoApplication.class);

        // Register the initializer manually
        app.addInitializers(new MyCustomContextInitializer());

        app.run(args);
    }
}
Use code with caution.
Option B:
Register via application.properties
Alternatively, you can register it declaratively within your src/main/resources/application.properties configuration file:propertiescontext.initializer.classes=com.example.demo.initializer.MyCustomContextInitializer

Use code with caution.

Option C: Register in Integration TestsIf you only need this initialization logic during testing, register it using the @ContextConfiguration annotation on your test class:
java

package com.example.demo;

import com.example.demo.initializer.MyCustomContextInitializer;
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.ContextConfiguration;

@SpringBootTest
@ContextConfiguration(initializers = MyCustomContextInitializer.class)
class DemoApplicationTests {

    @Test
    void contextLoads() {
        // Test context will load with "performance-mode" profile active
    }
}
Use code with caution.
Common Use CasesSpring Cloud / Microservices: Setting up fallback configurations or reading early data from a remote configurations vault before bootstrap.

Dynamic Property Overrides: Reading sensitive files safely from a specific server path and attaching them to the environment.

Test Container Setup: Injecting dynamic database ports generated by Testcontainers during integration tests directly into Spring's environment properties.

===============
This code is an implementation of a Spring ApplicationContextInitializer.

Its main purpose is to programmatically configure the Spring Environment before the application context is refreshed (meaning, before any Spring beans are actually created or initialized).

Here is a step-by-step breakdown of what each part is doing:

1. Accessing the Environment
Java
ConfigurableEnvironment environment = applicationContext.getEnvironment();

What it does: It grabs the application's environment.

Why: The Environment represents the profile-driven and property-driven aspects of the application. To change profiles or add properties programmatically, you need access to this object.

2. Activating a Profile Programmatically
Java
environment.addActiveProfile("performance-mode");
What it does: It dynamically activates a Spring profile named performance-mode.

Why: Normally, profiles are set in application.properties or via command-line arguments (like -Dspring.profiles.active=prod). Doing it here guarantees that the "performance-mode" profile is always active when this initializer runs, allowing you to load specific beans or configurations annotated with @Profile("performance-mode").

3. Injecting a Dynamic Property Source
Java
Map<String, Object> customProperties = Map.of("dynamic.api.timeout", "5000");
MapPropertySource propertySource = new MapPropertySource("myCustomSource", customProperties);
environment.getPropertySources().addFirst(propertySource);
What it does:

It creates a map containing a key ("dynamic.api.timeout") and a value ("5000").

It wraps that map inside a Spring MapPropertySource named "myCustomSource".

It injects this source using .addFirst().

Why the .addFirst() matters: Spring searches for properties in a specific order. By placing your custom source first, this property will override any matching property found in application.properties, application.yml, or system environment variables. Any bean that subsequently injects @Value("${dynamic.api.timeout}") will receive "5000".

Summary: Why use this?
This pattern is incredibly useful when you need to fetch configuration details from an external source (like HashiCorp Vault, AWS Parameter Store, or a database) before the rest of your Spring application starts up and tries to configure its beans.
