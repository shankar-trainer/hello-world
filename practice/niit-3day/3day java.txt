Custom Banner Management in Spring Boot Startup Messages
Alexander Obregon

Spring Boot applications greet developers with a console banner when they start up. Most leave it untouched, but personalizing it can be surprisingly handy for projects that run in several environments or go through frequent builds. A custom banner can show details like the version, Git branch, active profile, or deployment timestamp. It’s a small addition that helps communicate what’s running and where, right at startup, without opening a dashboard or digging through logs.

How the Banner System Works
Spring Boot’s banner system is one of the first things that runs during startup, long before the application context is ready. It’s part of the SpringApplication initialization process, which sets up the environment, prepares property sources, and then prints a banner to the console or log output. This happens early enough that you can rely on it to display information from environment variables or build metadata but not yet beans or autowired components.

At its core, the banner feature serves two purposes: to give a visual marker of startup and to present basic metadata that helps identify the instance or environment being launched. Teams working with several microservices often use banners to make logs easier to spot during deployment or local testing. When done well, it can save a few seconds of confusion about which service you’re watching among many terminals running at once.

Banner Loading Process
Spring Boot looks for a banner file during startup, starting with banner.txt in the classpath. If found, that file’s contents are printed during startup instead of the default Spring Boot logo. The banner can include plain text, ASCII art, or property placeholders that resolve dynamically from the environment.

Here’s a minimal banner.txt file that references some of the most common placeholders:

${spring.application.name}
Build Version: ${build.version}
Active Profile: ${spring.profiles.active}
When the application runs, those placeholders are replaced with their actual values pulled from environment properties. For instance, if your application.properties file contains spring.application.name=InventoryService, the console output will include that name automatically.

You can change where Spring Boot looks for this file by adjusting application.properties:

spring.banner.location=classpath:config/banner.txt
That line tells Spring Boot to load the banner from a custom location inside the config folder. The path can also be a filesystem path with file: or a classpath resource with classpath:

Some developers prefer programmatic control instead of a static file. You can do that by setting a banner directly on the SpringApplication instance before running it:

@SpringBootApplication
public class BannerExampleApp {
    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(BannerExampleApp.class);
        app.setBanner((env, source, out) -> out.println("Custom startup message for " 
            + env.getProperty("spring.application.name", "Unnamed App")));
        app.run(args);
    }
}
That small lambda gives you a quick way to print a one-line banner that still responds to environment data. The Environment object is available, but other beans are not yet initialized, which makes this stage perfect for lightweight metadata output.

Spring Boot loads its banner from a text source. Current versions look for banner.txt by default or for a location you set with spring.banner.location. Image-based banners were removed in Spring Boot 3, so only text banners are supported. Placeholders inside a text banner still work and are replaced from the environment at startup.

You can set spring.main.log-startup-info=true to print general startup information such as the application name and active profiles, but it doesn’t report banner configuration details or which banner file was used.

Banner Modes
Banner display behavior can be tuned with the spring.main.banner-mode property. It accepts three values that control how and where the banner appears.

console prints to the standard output stream (System.out).
log writes the banner through your logging configuration instead.
off disables the banner entirely.
A project that uses a continuous integration environment may prefer to log banners rather than print them to the console, keeping terminal output less cluttered.

Here’s how you can switch modes in your configuration file:

spring.main.banner-mode=log
That sends the banner to the logging system. When your logs are managed by something like Logback or Log4j2, the banner appears at the top of your log output.

If you’d rather disable the banner completely for automated testing or scripted deployments, you can do so like this:

spring.main.banner-mode=off
For applications that use multiple profiles, it can also make sense to control banner visibility per environment. The following code uses an environment-specific YAML configuration to handle that:

spring:
  main:
    banner-mode: console

---
spring:
  config:
    activate:
      on-profile: staging
  main:
    banner-mode: log

---
spring:
  config:
    activate:
      on-profile: prod
  main:
    banner-mode: "off"
This prints the banner to the console during local development, logs it in staging for verification, and disables it entirely in production.

Banner modes can also be changed programmatically when starting the application. This is useful if your build system wraps SpringApplication.run with extra logic that decides where the banner goes:

SpringApplication app = new SpringApplication(BannerExampleApp.class);
app.setBannerMode(Banner.Mode.LOG);
app.run(args);
That one line moves the banner output to your logging configuration, which is handy for remote deployments where the console output isn’t directly visible.

Each of these banner behaviors can be mixed with custom banners, so you can still include environment data or Git metadata regardless of where the output goes. That flexibility makes it practical for everything from local development to cloud-based services running through CI/CD pipelines.

Creating Dynamic and Context-Aware Banners
A static banner is nice for branding, but a dynamic one can make startup messages actually useful. When teams deploy across multiple environments, the banner can become an instant source of truth about what version is running, which profile is active, and where it’s running. Spring Boot makes that possible by allowing banners to be created programmatically or combined with data placeholders that update automatically from environment properties. It’s a lightweight feature that can communicate the build identity before the application even starts handling traffic.

Implementing a Custom Banner Programmatically
The Banner interface gives full control over how the banner appears. It’s invoked early in the startup process, just after environment variables are available but before any beans are initialized. This makes it ideal for printing configuration data or build information that doesn’t rely on other components.

Here’s a simple implementation that prints out build and environment details at startup:

import org.springframework.boot.Banner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.core.env.Environment;
import java.io.PrintStream;

@SpringBootApplication
public class CustomBannerApp {

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(CustomBannerApp.class);
        app.setBanner(new InfoBanner());
        app.run(args);
    }

    static class InfoBanner implements Banner {
        @Override
        public void printBanner(Environment env, Class<?> source, PrintStream out) {
            String app = env.getProperty("spring.application.name", "App");
            String version = env.getProperty("build.version", "Unknown");
            String profile = env.getProperty("spring.profiles.active", "default");
            out.println("======================================");
            out.println(" Application: " + app);
            out.println(" Version: " + version);
            out.println(" Active Profile: " + profile);
            out.println("======================================");
        }
    }
}
This method prints environment-specific details in a consistent format. It works well when the build process adds variables like build.version from Maven or Gradle filtering.

Some teams prefer adding a visual cue for production builds. You can use ANSI color codes for that purpose. Spring Boot supports color rendering in banners by default:

out.println("\u001B[33m" + "Running Production Build" + "\u001B[0m");
That line prints the message in yellow text. It can help developers quickly spot which instance they’re working with, especially when switching between environments.

Combining Dynamic Data with a Text Banner
While programmatic banners are flexible, many projects still rely on banner.txt because it’s simple to edit and works across builds without code changes. Property placeholders inside that text file are replaced automatically when the application starts. That makes it easy to blend static visuals with dynamic values.

A basic banner.txt can look like this:

Welcome to ${spring.application.name}
Build: ${build.version}
Profile: ${spring.profiles.active}
When the application runs, these placeholders resolve from environment properties. You can enrich it by adding your own variables in application.properties:

build.version=@project.version@
deployment.region=us-central
Now you can extend your banner to show deployment regions or any other metadata that fits your workflow.

For cases where banners differ between environments, such as development and staging, you can store separate files and load them conditionally. This can be done through spring.banner.location and Spring profiles:

spring:
  banner:
    location: classpath:banner-dev.txt
  config:
    activate:
      on-profile: dev
---
spring:
  banner:
    location: classpath:banner-prod.txt
  config:
    activate:
      on-profile: prod
That way, your local builds can display a friendly banner while production shows a minimal one with deployment identifiers. It keeps everything context-aware without adding logic inside your code.

Integrating Git Metadata
Version control metadata adds a helpful layer to banners, especially when debugging a deployment. Spring Boot supports reading git.properties at runtime, and build plugins can generate that file during your build. This file contains information like the commit hash, branch name, and build time.

In Maven, you can generate git.properties with the git-commit-id-maven-plugin. Projects that use the spring-boot-starter-parent already get plugin management for it, so a basic declaration looks like this:

<build>
  <plugins>
    <plugin>
      <groupId>io.github.git-commit-id</groupId>
      <artifactId>git-commit-id-maven-plugin</artifactId>
    </plugin>
  </plugins>
</build>
This setup writes a git.properties file under target/classes when the build runs. Spring Boot then auto-configures a GitProperties bean from that file, so the git values can appear on the /actuator/info endpoint when Actuator is on the classpath and the info endpoint is exposed. If you want banner output to include git commit and branch data, you can either read git.properties inside a custom Banner implementation or add git.properties as an extra property source early in startup so the Environment exposes those git.* keys for placeholders in banner.txt.

For deeper customization, developers can load the Git metadata manually. Here’s how that could look in a banner implementation:

import java.util.Properties;
import java.io.InputStream;

public class GitInfoPrinter {
    public static void printGitInfo(PrintStream out) {
        try (InputStream input = GitInfoPrinter.class.getResourceAsStream("/git.properties")) {
            if (input == null) return;
            Properties props = new Properties();
            props.load(input);
            out.println("Commit: " + props.getProperty("git.commit.id.abbrev", "Unknown"));
            out.println("Branch: " + props.getProperty("git.branch", "N/A"));
        } catch (Exception e) {
            out.println("Git information unavailable");
        }
    }
}
That example reads directly from the generated file, giving full control over what gets printed and how it’s formatted. Combining Git information with profile and version data helps track exactly which build is deployed without checking logs or artifact metadata.

Managing Environment Variables and System Properties
Environment variables and system properties give context to where an application is running. They can identify regions, node IDs, or runtime configurations that aren’t tied to build files. Spring Boot passes these variables to the Environment object, which can be used inside any banner implementation.

This code prints the deployment region and server name when available:

String region = env.getProperty("DEPLOY_REGION", "unknown");
String host = System.getenv().getOrDefault("HOSTNAME", "local");
out.println("Region: " + region);
out.println("Server: " + host);
Those two lines can be enough to confirm which cluster or container instance you’re connected to. They’re particularly helpful in cloud setups where multiple instances of the same service run side by side.

If you’re working with container orchestration tools like Kubernetes, environment variables such as POD_NAME or NAMESPACE can be printed as part of the banner to identify each running pod:

String pod = env.getProperty("POD_NAME", "unknown");
String namespace = env.getProperty("NAMESPACE", "default");
out.println("Pod: " + pod);
out.println("Namespace: " + namespace);
For projects that want to centralize configuration, environment data can also be pulled from a custom configuration service through EnvironmentPostProcessor. That allows injecting extra values before the banner prints. Here’s a short example:

import org.springframework.boot.EnvironmentPostProcessor;
import org.springframework.core.env.ConfigurableEnvironment;
import org.springframework.core.env.MapPropertySource;
import java.util.Map;

public class BannerEnvironmentProcessor implements EnvironmentPostProcessor {
    @Override
    public void postProcessEnvironment(ConfigurableEnvironment env, SpringApplication app) {
        Map<String, Object> customData = Map.of("deploy.info", "staging-build");
        env.getPropertySources().addLast(new MapPropertySource("customDeployData", customData));
    }
}
With that registered in META-INF/spring.factories, your banner can print new environment fields without modifying core configuration files. This keeps dynamic information available early in the lifecycle while keeping your build flexible for multiple environments.

Dynamic banners bridge build data, runtime context, and configuration values in a way that’s both readable and instantly useful. They’re one of the easiest ways to make a Spring Boot service self-descriptive from the moment it starts.

Conclusion
Spring Boot’s banner feature runs at a moment when the environment is ready but the rest of the application hasn’t fully started yet. That timing makes it perfect for adding build data or environment details right where developers can see them. The process itself is simple and reliable. It reads configuration, replaces placeholders with live values, and prints the message before the context loads. A banner can come from a custom class or a text file, but the same sequence happens behind the scenes. It’s a small feature that gives immediate awareness of what version is running and where, making startup logs feel more intentional and connected to the system they represent.

Diagnose HikariCP / DBCP / c3p0 connection pool exhaustion 

Connection pool exhaustion in Spring Boot happens when all available database connections are in use, and new requests must wait or fail with a timeout error.
Common Causes
    • Slow queries: Queries take too long and keep connections busy.
    • Connection leaks: Code borrows a connection but fails to close it.
    • High concurrency: Traffic exceeds the maximum pool size limit.
    • Under-sized pool: The maximum pool size is too small for the load.

How to Diagnose
1. Enable Pool-Specific Logging
Add debug or trace logging in your application.properties or application.yml to track connection usage.
    • HikariCP (Default in Spring Boot):
      properties
      ://level.com.zaxxer.hikari=DEBUG
      ://level.com.zaxxer.hikari.HikariConfig=DEBUG
      Use code with caution.
      HikariCP logs warnings automatically when connections are acquired slowly or when the pool is exhausted. Look for logs containing Apparent connection leak detected.
    • Apache DBCP2:
      properties
      logging.level.org.apache.commons.dbcp2=DEBUG
      Use code with caution.
    • C3P0:
      properties
      ://level.com.mchange.v2.c3p0=DEBUG
      Use code with caution.
2. Monitor Active Metrics with Actuator
Add Spring Boot Actuator to your project to inspect real-time pool metrics.
    1. Add the dependency:
       xml
       <!-- Maven -->
       <dependency>
           <groupId>org.springframework.boot</groupId>
           <artifactId>spring-boot-starter-actuator</artifactId>
       </dependency>
       Use code with caution.
    2. Expose the endpoints in application.properties:
       properties

To resolve Tomcat or WildFly deployment failures when migrating or running a Spring Boot application on an external application server, adjust your build configuration to prevent server and logging conflicts. [1, 2]

Common Fixes for WildFly / External Server Failures
    • Change Packaging to WAR: Modify your project configuration to produce a WAR file instead of an executable JAR.
    • Extend SpringBootServletInitializer: Update your main application class to extend SpringBootServletInitializer so the external servlet container can initialize it.
    • Mark Embedded Tomcat as Provided: Exclude or scope the embedded Tomcat dependencies as provided so they do not conflict with the application server's runtime.

    • Add Missing Servlet APIs explicitly: For Spring Boot 3.x, add the jakarta.servlet-api dependency with a provided scope if servlet initialization fails

•Configure correct JVM args for containerised Java workloads (heap, GC, container-aware flags)


Configure JVM arguments for containerized Java workloads by enabling container awareness and setting explicit memory limits to prevent out-of-memory crashes.
Key Container-Aware Flags
Modern Java versions (Java 10+) automatically recognize container memory and CPU limits, but older versions or specific setups need explicit flags.
    • -XX:+UseContainerSupport: Enables container awareness so the JVM reads limits from cgroups (enabled by default in Java 10+).
    • -XX:MaxRAMPercentage=75.0: Sets the maximum heap and non-heap memory the JVM can use as a percentage of the container's total memory limit (leave room for off-heap memory like metaspace and thread stacks).
    • -XX:InitialRAMPercentage=50.0: Sets the initial memory allocation percentage.
    • -XX:MinRAMPercentage=50.0: Sets the minimum memory allocation for small containers.
Garbage Collector (GC) Selection
Choose a garbage collector based on your latency and throughput needs.
    • G1GC (Default for Java 9+): Best for balanced throughput and low latency. Add -XX:+UseG1GC.
    • ZGC (Low Latency): Best for massive heaps with ultra-low pause times (Java 15+). Add -XX:+UseZGC.
    • ParallelGC (High Throughput): Best for batch jobs where pause time does not matter. Add -XX:+UseParallelGC.
Recommended Example Configuration
Use this production-ready baseline for a modern Java container (Java 17+):
bash
java -XX:+UseContainerSupport \
     -XX:MaxRAMPercentage=75.0 \
     -XX:+UseG1GC \
     -XX:+ExitOnOutOfMemoryError \
     -jar app.jar
Use code with caution.
    • -XX:+ExitOnOutOfMemoryError: Forces the container to crash immediately on a java.lang.OutOfMemoryError, allowing the orchestrator (like Kubernetes) to restart a clean instance.
